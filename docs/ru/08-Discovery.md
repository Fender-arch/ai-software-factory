## Назначение

Превратить идею заказчика в черновик спецификации с достаточной ясностью для архитектуры и планирования — с учётом IT-грамотности заказчика.

Интервью должно **закрыть все применимые разделы ТЗ** до ревью владельца, если заказчик не поставит **паузу** и не передаст оставшееся разработчику.

**Применимые** — не фиксированная анкета: после идеи и типа решения Discovery **подстраивает перечень разделов под эту задачу** — каркас всегда, модули типа/формы когда нужны, дополнительные подразделы если без них нельзя реализовать v1, и пропускаемые модули снимаются если они не про эту задачу (например публичный каталог услуг у внутреннего бота записи).

Приёмы качества (уточняющий проход, не угадывать вместо `[NEEDS CLARIFICATION]`, чеклисты как «unit tests for English») адаптированы из [GitHub Spec Kit](https://github.com/github/spec-kit) (MIT). CLI Spec Kit в ASF **не** подключается. Путь заказчика — по-прежнему обход разделов ТЗ.

## Каналы

- **Mini App** project workspace (основной) — текст + попап **«Варианты ответа»**. Новый проект: приветственный попап, затем вопросы. В чате проекта — **полоса прогресса** (серый фон, зелёная заливка); API по-прежнему считает `сделано/всего` по адаптированному каркасу, а подпись для заказчика — **процент** или «ещё пара уточнений», не список разделов. Под полосой — человеческий русский `customer_hud` (не сырой статус / mode / этап / topic id). Мультивыбор в чат уходит **лейблами** чипов; «Сейчас напишу» ждёт дописанный текст, и только потом следующий вопрос. Реплика ассистента — только следующий вопрос.
- Telegram **голос** (Mini App или бот) → Whisper STT → текст (тот же пайплайн)
- DM бота: переходный режим до Mini App; затем уведомления + deep links

UX-требования: [14-Telegram-Customer-UX.md](14-Telegram-Customer-UX.md).

## Режимы заказчика (вход)

| Режим | Когда | Исход |
|-------|-------|-------|
| Create | Новый проект | Полный Discovery FSM → черновик ТЗ → владелец |
| Change | Существующий проект | Уточнения/правки → обновление KG, gaps/противоречия; возможный возврат стадий или эскалация |
| Implementation feedback | После ознакомления с поставленным MVP | Классификация замечания; проверка vs утверждённое ТЗ/KG; эскалация противоречий |

## Высокоуровневый FSM

```
PROJECT_CREATED
  → UNDERSTANDING_IDEA
  → BUSINESS_CONTEXT
  → USERS
  → FUNCTIONAL
  → DATA
  → NON_FUNCTIONAL
  → INTEGRATIONS
  → ACCEPTANCE
  → RISKS
  → REVIEW
  → READY_FOR_OWNER
```

На каждой стадии — **один или несколько разделов ТЗ**. Переходы могут идти назад при противоречиях или пробелах.

## Ход под управлением LLM (DEC-008)

С DEC-008 **LLM-интервьюер ведёт реплику диалога**, когда `DISCOVERY_ENGINE` резолвится в `llm` (по умолчанию `auto`: llm, если `LLM_PROVIDER` не `stub`; `fsm` принудительно включает детерминированный запасной путь):

**Прод:** гибкое интервью **не** включается при `LLM_PROVIDER=stub`. Нужно `LLM_PROVIDER=groq` (и `GROQ_API_KEY`), чтобы `auto` пошёл в LLM. `DISCOVERY_ENGINE=fsm` или stub сохраняет покрытие, но вопросы идут из перефразированного FSM (без меню заголовков каталога).

- На каждое сообщение заказчика LLM получает адаптированный каркас как **внутренний** чек-лист покрытия (статус раздела и что уже зафиксировано; DEC-014: заказчик не видит этот список как анкету). Она отвечает с подтверждением, отвечает на встречные вопросы, выбирает следующий раздел (каркас первым) и может закрыть **несколько разделов за одно сообщение** через структурированные `captured`-обновления (канонический английский в сводках). Промпт: `prompts/discovery-interview.md`.
- Кнопки-варианты **генерируются LLM на каждый ход** из контекста диалога и проходят санитизацию в коде (максимум 5, ограничение длины, эксклюзивный чип «обсудить с разработчиком» всегда добавляется кодом). Чипы — подсказки к **текущему** вопросу, не меню разделов.
- Детерминированное ядро сохраняет гарантии: записи в KG делает только код (неизвестные id разделов отбрасываются), `ready_for_owner` исполняется, только когда не осталось применимых разделов **и** пройден порог качества (иначе ход продолжается мягким «ещё пару вещей для сборки» — без списка `title_ru`), а интенты пауза / продолжить / «готово» / «остальное с разработчиком» распознаются до вызова LLM.
- Любой сбой LLM или невалидный JSON откатывает ход на детерминированный FSM — заказчик всегда получает ответ; если LLM-путь был включён, пишется WARNING. Тесты работают на stub/fake-провайдерах и продолжают проходить FSM-путь.

На стадии `REVIEW` дополнительно идёт **проход уточнений** (максимум 5 вопросов с высоким влиянием, по одному, с рекомендованным вариантом). Остаток после лимита уходит в `OpenQuestion` или Assumptions черновика. Это не новая стадия FSM.

После уточнений — короткий **финальный проход** (всё ещё `REVIEW`): есть ли что добавить; какую сумму закладывают, если хотят назвать цифру; есть ли готовая постановка (файл или текст из ChatGPT / другой нейросети). Текст из txt/md/docx попадает в ТЗ. «готово» пропускает остаток прохода и отправляет черновик.

Когда черновик отправлен, заказчик может **скачать то же ТЗ** (Markdown, Word, PDF) в Mini App. В Telegram файл уходит в чат с ботом (WebView не даёт надёжно сохранить через `<a download>`).

## Каркас ТЗ (минимум, чтобы начать разработку)

Каталог: `discovery/tz_outline.py`. Сжатый из ГОСТ 34.602-2020, ISO/IEC/IEEE 29148 и практических PRD под **простые** MVP ASF.

Каталог — это **библиотека**, а не скрипт интервью. `discovery/adapt.py` собирает план на проект:

1. **Каркас** (не пропускаем): цель, тип решения, успех MVP, вне объёма, must-have, главный сценарий, приёмка, сроки, бюджет, контакты, канал связи, **законы / 152-ФЗ**, риски
2. **Модули типа / формы** — страницы/CTA, бот vs Mini App, ресурсы API, триггер ИИ и т.д.
3. **Модули по сигналам задачи** — правила записи, уведомления, потребители API, голос, путь при сбое — только если идея это требует
4. **Динамические подразделы** (`custom:…`) — эвристики добавляют узкие вопросы под задачу (например кто выбирает слот); Groq может добавить до 8 при `LLM_PROVIDER=groq`
5. **Пропуски** — публичная подпись / офер / CTA / бренд / страницы / **продвижение (SEO, реклама)** / **референсы и направление дизайна**, если нет публичного присутствия; Mini App уже выбран → не спрашиваем «бот или Mini App»
6. **Формулировки** — после описания идеи оставшиеся **вопросы и кнопки-варианты** переписываются под эту задачу **и под следующие ответы**. Если заказчик просит приложение для Android или iOS, эти пункты появляются в вопросе про тип решения и фиксируют `mobile_native` (DEC-010). Id чипов каталога те же; подписи меняются, лишние скрываются, могут появиться дополнительные `ctx:*` из уже сказанного (эвристика всегда; Groq уточняет при `LLM_PROVIDER=groq`). Добавленные и пропущенные заголовки остаются **внутри** — заказчику меню разделов не зачитываем (DEC-014).

Стадии FSM те же. Агент по-прежнему двигается **на один раздел за ответ**. Виртуальные узлы консоли владельца следуют адаптированному перечню (отдельный тип сущности Section не вводим).

| Раздел | Что нужно знать, чтобы начать код |
|--------|-----------------------------------|
| Цель и проблема | Какую боль закрываем |
| Тип решения | сайт / бот / API / ИИ-агент / автоматизация / учёт / интеграция / нативное мобильное |
| Как сейчас | As-is процесс |
| Успех MVP | Как поймём, что v1 ок |
| Вне объёма | Явные non-goals |
| Сроки реализации | Обязательная vs ожидаемая дата |
| Бюджет | Есть ли бюджет и порядок суммы |
| Контакты | Имя, телефон, email, Telegram; кто принимает решения |
| Способ связи | Звонок, Telegram, почта, мессенджер |
| Продвижение / SEO | В v1: поиск, реклама, аналитика — или не в объёме разработки (влияет на оценку) |
| Пользователи и роли | Кто действует |
| Доступ | Публично / свои / логин / ключ API |
| Обязательные функции | Возможности v1 |
| Главный сценарий | Один счастливый путь |
| Специфика типа | Страницы/CTA, бот vs Mini App, ресурсы или триггер ИИ |
| Публичная подпись / офер / CTA / бренд / референсы / дизайн | Только если есть публичное присутствие. Спросить примеры и *что* в них взять; направление: спокойный лаконичный vs современный motion vs кричащий 3D (влияет на оценку) |
| Подразделы по задаче | Запись, уведомления, потребители API, голос, путь при сбое — если идея это требует |
| Динамические подразделы | Дополнительные вопросы под *эту* задачу, если каталога мало |
| Данные | Что храним и кто правит |
| Язык / UX | Локаль, устройство, бренд (можно пропустить, если уже ясно) |
| Где крутится | Хостинг, нагрузка, ПДн |
| Законы и ПДн | 152-ФЗ (согласие/политика), cookies, маркировка рекламы, отрасль (влияет на оценку) |
| Интеграции | Почта, таблицы, CRM, нет |
| Приёмка | Как заказчик проверит «готово» |
| Кто обслуживает | Оператор после поставки |
| Риски | Блокеры / неизвестные |

Типы продукта (DEC-003 + DEC-010): `website` | `telegram_bot` | `rest_service` | `ai_automation` | `mobile_native`. Формулировки заказчика мапятся на эти типы:

| Заказчик просит | Тип |
|-----------------|-----|
| Сайт / лендинг / витрина | `website` |
| Telegram-бот | `telegram_bot` |
| REST API | `rest_service` |
| База + админка | `rest_service` (`task_shape=database_tool`) |
| Связка систем | `rest_service` (`task_shape=integration`) |
| ИИ-агент или автоматизация процесса | `ai_automation` |
| Нативное приложение Android / iOS | `mobile_native` |

## Если заказчик не знает ответ

У каждого раздела есть **варианты**. По DEC-008 чипы **пишет LLM на каждый ход** из контекста диалога (варианты каталога остаются запасной подсказкой): если заказчик сказал, что запись идёт в WhatsApp, чипы называют WhatsApp, а не общее «мессенджеры». Безопасные дефолты могут быть помечены как **рекомендуем** (например «без оплаты в v1», «с нуля»). Цель, бюджет и контакты **не** рекомендуем. Там, где уместно (вне объёма, роли, интеграции и т.п.), можно отметить **несколько пунктов** и нажать «Отправить». Пауза, «обсудить с разработчиком» и «готово» срабатывают сразу.

**Кнопка-вариант** закрывает раздел **кроме** разделов с контентом для сборки (публичное имя, список услуг, контакт посетителя, цвета бренда, **что взять из референса**, куда уходит заявка, хост/домен если «уже есть сервер»): их закрывает только текст или явная заглушка («пока заглушки», «референсов нет»). **Размытый свободный текст** («удобно», «быстро», «как обычно») раздел **не** закрывает: тот же вопрос задаётся ещё раз, затем эскалация разработчику.

Публичные разделы и разделы с `needs_substance` **не** закрываются сами по ключевым словам из описания идеи — их спрашиваем сразу. Если заказчик не знает или выбирает «обсудить с разработчиком», раздел эскалируется и **не** заполняется догадкой.

Одни URL без «что копировать», чипы типов услуг без текстов или заглушки, «заявки в канал» без `@канала` и «рядом с существующим сервером» без адреса — недостаточно, переспрашиваем. Короткий срок плюс кричащий 3D/вау повторяем на `design_direction` (и в уточняющем проходе, если всё же проскочило).

Заказчик может:

- **«пауза»** — остановить без отправки черновика ТЗ
- **«продолжить»** — вернуться к текущему разделу
- **«остальное с разработчиком»** — открыть незакрытые разделы (и оставшиеся уточнения) как вопросы и всё же отправить черновик
- **«готово»** — отправить черновик **только если** все разделы закрыты или эскалированы **и** выполнен порог качества (или остаток качества эскалирован); иначе агент задаёт ещё один вопрос для сборки (без списка заголовков каталога)

Короткое сообщение и одна фраза про идею **не** финализируют Discovery.

## Порог качества (unit tests для ТЗ)

Детерминированные проверки в `discovery/quality.py` и `knowledge/coverage.py` (это не тесты реализации):

- Есть хотя бы одно проверяемое требование (конкретный объект/результат)
- Измеримый успех MVP (`success_mvp` закрыт или эскалирован)
- Объём ограничен (`out_of_scope` закрыт или эскалирован)
- Опционально: главный сценарий, проверяемая приёмка, нет висящих blocking-уточнений

Keyword-покрытие разделов ≥ 0.4 **не** заменяет этот порог.

## Статусы проекта (runtime)

`NEW` → `INTERVIEW` → `ANALYZING` → `WAITING_CUSTOMER` → `WAITING_OWNER` → `WAITING_CLIENT_ESTIMATE` → `READY` → `ARCHIVED`

## Критерии готовности (черновик)

- Применимые разделы ТЗ закрыты или отданы разработчику
- Порог качества выполнен или остаток эскалирован
- Зафиксирован объём MVP и вне объёма
- Архитектурная достаточность (можно планировать простую поставку)
- Нет блокирующих противоречий (или эскалировано владельцу)

## Выходные артефакты

Из Knowledge Graph:

- Vision / постановка проблемы
- User stories с Given–When–Then для главного пути
- Разделы ТЗ (по **адаптированному** каркасу этой задачи)
- Списки `FR-###` / `SC-###`
- Assumptions и Clarifications (ответы уточняющего прохода)
- Открытые вопросы (включая передачу разработчику)
- Черновик объёма MVP
- Рекомендации для ревью владельца (gaps / противоречия reviewer-скана)

## HITL

Владелец получает Telegram-сообщение, как только **новый** черновик ТЗ сохранён (бот, Mini App или API): имя проекта, id, **эвристическая оценка поставки** (часы × `ASF_ESTIMATE_HOURLY_RATE`, по умолчанию 3000 RUB/час), короткое обоснование на русском (тип продукта, must/should/could, открытые вопросы, риски; потолок 80 ч для простого MVP), ориентир бюджета заказчика из раздела Discovery `budget` (пометка, если оценка выше/ниже диапазона — чип **не** котировка) и `/review <id>`. Это подсказка для HITL владельца, не цена клиенту. Число детерминированное (без LLM). Открытые вопросы и риски увеличивают часы; их не «закрывают» догадками. Оценка лежит в `payload.estimate` артефакта `draft_tz` и снова показывается в `/review`. После `approve` считается **отдельная клиентская смета** (`payload.client_estimate` + `payload.client_estimate_report`, DEC-012), проект переходит в `WAITING_CLIENT_ESTIMATE`. Заказчик подтверждает или просит обсудить в Mini App; Planner стартует только после confirm (`READY`). «Нужно обсудить» возвращает `WAITING_CUSTOMER`. Замечания к реализации, противоречащие утверждённому ТЗ, поднимают `HumanDecisionRequired`.

Пока черновик у владельца (`WAITING_OWNER`), заказчик может присылать дополнения. Они всегда фиксируются как требования и попадают в черновик ТЗ; это не обходит ревью и не запускает планирование. В Mini App можно скачать то же ТЗ (Markdown / Word / PDF), что ушло владельцу; в Telegram копия приходит документом в чат с ботом.

Если применимые разделы ТЗ ещё не закрыты (например, в каркас добавили контентные вопросы после отправки черновика), Discovery **снова задаёт эти вопросы**. Открытие Mini App или сообщение спрашивает следующий пробел; проект возвращается в `WAITING_CUSTOMER`, пока пробелы не закрыты или не переданы разработчику, затем черновик обновляется для владельца.
